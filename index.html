QA ACADEMY

🚀 Guia Prático: seu primeiro teste de carga no TechEduca

Você vai aprender, passo a passo, como simular vários usuários acessando uma aplicação ao mesmo tempo usando o Grafana Cloud k6, direto no navegador e sem instalar programas.

👥 5 usuários virtuais
⏱️ 10 segundos
🌐 TechEduca

1Crie sua conta no Grafana Cloud

Cada aluno deverá utilizar sua própria conta. Clique no botão abaixo para acessar o Grafana e iniciar o cadastro.

Criar minha conta

Preencha os dados solicitados pelo Grafana e conclua o cadastro. Se for solicitado confirmar seu e-mail, faça a confirmação antes de continuar.

Objetivo desta etapa: ter uma conta própria e conseguir acessar o Grafana Cloud.

2Entre no Grafana Cloud

Depois de criar a conta, faça login no Grafana Cloud.

Entrar no Grafana Cloud

Após o login, aguarde o painel principal carregar completamente.

✅ Você chegou ao lugar certo se: estiver dentro do ambiente do Grafana Cloud e conseguir visualizar o menu de navegação.

3Encontre a área de testes

No menu lateral do Grafana, procure a opção:

Testing & synthetics

Clique nela para abrir as ferramentas relacionadas a testes.

4Abra Performance

Dentro de Testing & synthetics, clique em:

Performance

É nessa área que trabalharemos com testes de desempenho e carga.

5Entre em Projects

Na área de Performance, localize e clique em:

Projects

Os projetos organizam os testes que você criar no Grafana Cloud k6.

6Abra o projeto disponível

Localize o projeto padrão da sua conta. Se aparecer Default project, clique nele.

Testing & synthetics → Performance → Projects → Default project

O nome ou a organização da tela pode variar um pouco conforme a conta, mas o objetivo é entrar no projeto onde o teste será criado.

7Crie um novo teste

Dentro do projeto, procure a opção para criar um novo teste e avance até chegar à tela:

Create a test

Não configure nada além disso ainda. Primeiro vamos escolher o tipo correto de teste.

8Escolha Manual

Na tela de criação, escolha como o teste será preparado:

✋ Manual ⭐

Você configura o teste e entende cada etapa. É esta opção que vamos usar.

✨ AI-assisted

A IA auxilia na criação do teste a partir de uma descrição. Não usaremos agora.

9Selecione Web application

Agora informe o tipo de sistema que será testado:

🌐 Web application ⭐

Aplicações web. Escolha esta opção para o TechEduca.

🔗 HTTP API

APIs HTTP, REST e GraphQL.

🟣 Other protocols

WebSocket, gRPC e outros protocolos.

10Abra o Test Builder

Nesta atividade, não usaremos Record user flow nem Write a script.

Role a página até encontrar:

Can't find what you need? Try the Test Builder →

Clique em Try the Test Builder.

11Entenda o que vamos montar

Usuários virtuais → acessam uma publicação do TechEduca → durante um tempo definido → o Grafana registra o desempenho

🌐 Qual URL do TechEduca devo usar?

🥇 Preferencial: seu próprio TechEduca

Se você já publicou o TechEduca no GitHub Pages, use a URL do seu próprio projeto.

Exemplo:

https://seuusuario.github.io/TechEduca/

Assim, você executará o teste sobre a sua própria publicação.

🥈 Alternativa: TechEduca do professor

Se o seu projeto ainda não estiver publicado ou sua publicação estiver com problema, utilize o endereço disponibilizado pelo professor:

Abrir TechEduca do professor

⚠️ Não use localhost:3000. O teste será executado pelo Grafana Cloud. Por isso, a aplicação precisa estar publicada e acessível pela internet.

✅ Antes de continuar

Abra a URL que você escolheu em uma nova aba do navegador.

Se abriu corretamente, copie essa URL. Você deverá usar o mesmo endereço na configuração da requisição.

12Crie a requisição

Em SCENARIOS → Requests, crie a requisição que representará o acesso ao TechEduca.

NAME:

Acesso TechEduca

REQUEST: selecione GET.

URL: cole a URL do TechEduca que você escolheu e testou na etapa anterior.

🥇 Use sua própria URL do GitHub Pages sempre que ela estiver funcionando. Use a URL do professor somente como alternativa.

13O que significa GET?

O método GET solicita um recurso ao servidor. Neste teste, nosso usuário virtual está basicamente dizendo: "TechEduca, envie esse recurso para mim."

Neste primeiro teste não faremos login, cadastro, alteração de dados ou envio de formulário. Vamos observar o acesso a um recurso público.

14Deixe vazias as opções que não usaremos

Para este primeiro teste, não precisamos configurar tudo o que aparece na requisição:

Headers

Deixe vazio.

Query Params

Deixe vazio.

Variables

Deixe vazio.

Body

Deixe vazio.

Mais adiante usaremos apenas Checks para verificar a resposta.

15Configure o cenário: Executor

Em SCENARIO_1 → Options, encontre o campo Executor. Ele define como a carga será gerada.

Constant VUs ⭐

Mantém uma quantidade fixa de usuários virtuais durante um período. Usaremos este.

Shared iterations

Os usuários dividem um total de execuções.

Per VU iterations

Cada usuário executa uma quantidade definida de vezes.

Ramping VUs

A quantidade de usuários aumenta ou diminui gradualmente.

Constant Arrival Rate

Mantém uma taxa constante de novas execuções.

Ramping Arrival Rate

A taxa de execuções varia ao longo do teste.

16Entenda o que são VUs

VU = Virtual User, ou usuário virtual. É um usuário simulado pelo k6 para gerar carga sobre a aplicação.

Mexa no controle abaixo para visualizar a quantidade de usuários:

⚠️ 5 VUs não significam apenas 5 requisições. Durante o teste, os usuários virtuais podem repetir o cenário várias vezes.

17Configure o primeiro cenário

Agora preencha as opções do cenário:

CampoValor
NAMECenario_5_usuarios
EXECUTORConstant VUs
START TIME0s
VUS5
DURATION10s

Se aparecer Graceful Stop, mantenha o valor padrão.

"Mantenha 5 usuários virtuais acessando a URL escolhida do TechEduca durante 10 segundos."

18Adicione uma verificação (Check)

Não basta observar se o site respondeu rápido. Também queremos verificar se a requisição foi respondida corretamente.

Em Requests → Acesso TechEduca → CHECKS, configure:

HTTP status code → Equals → 200

200 OK indica que a requisição foi atendida com sucesso. Assim conseguimos observar desempenho e funcionamento.

19Faça a conferência final

Antes de executar, confira item por item:

🌎 Load zonesDefine de qual região a carga é gerada. Para este primeiro teste, mantenha a configuração padrão.
📏 ThresholdsSão critérios de aceitação de desempenho. Exemplo: definir que uma porcentagem das respostas deve ficar abaixo de determinado tempo. Não configuraremos isso neste primeiro teste.

20Execute o teste ▶️

⚠️ Espere a autorização do instrutor. Depois, clique em Create and run, aguarde a execução terminar e não feche a página durante o teste.

Quando a execução terminar, não se preocupe em entender todos os números de uma vez. Vamos analisar o resultado por partes.

Nosso objetivo não é decorar métricas. É aprender a responder: o sistema continuou funcionando? Como ele se comportou com a carga aplicada?

21Comece confirmando a execução

Antes de analisar qualquer gráfico, confira se o teste realmente terminou e se a carga executada corresponde ao que você configurou.

✅ Status

Verifique se a execução foi concluída.

👥 VUs

Confira quantos usuários virtuais foram utilizados.

⏱️ Duração

Confira por quanto tempo o cenário foi executado.

🌎 Região

Você também pode encontrar a região usada para gerar a carga.
🧠 Pergunta: o teste executado corresponde ao teste que você planejou?

22Veja o Cloud Insights

O Cloud Insights faz uma análise automática da execução e pode destacar boas práticas, problemas ou oportunidades de melhoria.

Os itens e as pontuações podem variar de um teste para outro. Por isso, não tente apenas copiar os números de um colega. Abra os tópicos disponíveis e leia o que o Grafana encontrou no seu teste.

Best Practice

Ajuda a identificar boas práticas e configurações que podem ser melhoradas.

Reliability

Pode indicar aspectos relacionados à confiabilidade da execução, como falhas HTTP.

System

Pode apresentar informações relacionadas à infraestrutura que gerou a carga.

⚠️ Atenção: uma pontuação alta em uma categoria não significa automaticamente que sua aplicação tem desempenho perfeito. Leia a explicação de cada item antes de concluir.

🔎 Faça assim: abra cada tópico → leia Explanation → veja se existe alguma orientação em Actions.

23Analise os Checks

Agora procure a área CHECKS. Ela mostra se as condições que você configurou foram atendidas durante o teste.

Neste exercício configuramos um Check para verificar se a resposta HTTP possui status 200.

Success Rate

Percentual das verificações que passaram.

Success Count

Quantidade de verificações aprovadas.

Fail Count

Quantidade de verificações que falharam.

⚠️ 100% de Success Rate não significa “100% de desempenho”. Significa que 100% das condições verificadas pelo Check foram atendidas.

🧠 Pergunte: nossa condição foi atendida? Houve alguma falha? O resultado mudou quando aumentamos a carga?

24Abra a aba Analysis 📊

Depois de conferir a execução, o Cloud Insights e os Checks, abra ANALYSIS → Explore test results.

Essa área permite escolher o que você quer analisar e como os dados serão apresentados.

1️⃣ Metrics

O que eu quero analisar?
Ex.: tempo de resposta, falhas, VUs ou iterações.

2️⃣ Aggregation

Como eu quero resumir esses dados?
Ex.: média, máximo, mediana ou percentil.

3️⃣ Gráfico

Como isso se comportou ao longo do teste?
Observe valores, mudanças, picos e tendências.
💡 Pense sempre nesta ordem: Metrics → Aggregation → Gráfico → Interpretação.

25Primeiro escolha a Metric

Metric é aquilo que você quer medir ou investigar. Antes de olhar o gráfico, pergunte: “O que eu quero descobrir?”

⏱️ Tempo de resposta

Procure métricas HTTP relacionadas ao tempo de resposta quando quiser investigar rapidez ou lentidão.

📨 Requisições

Use métricas relacionadas às requisições para observar o ritmo em que elas ocorreram.

❌ Falhas

Use métricas de falha para investigar se as requisições começaram a apresentar problemas.

👥 VUs

Mostra a quantidade de usuários virtuais ativos durante a execução.

🔁 Iterations

Representa execuções concluídas do cenário de teste.

⌛ Iteration Duration

Representa o tempo necessário para uma execução completa do cenário.

✅ Checks

Permite observar informações relacionadas às verificações executadas no teste.

👥 Max VUs

Indica a quantidade máxima possível/configurada de usuários virtuais, quando disponível para análise.

⚠️ A lista de métricas pode variar conforme o tipo de teste e os dados registrados. Você não precisa usar todas.

26Depois escolha a Aggregation

Uma métrica pode possuir muitos valores durante uma execução. Aggregation define como esses valores serão resumidos ou apresentados.

Metric responde: “O que estou medindo?”
Aggregation responde: “Como quero olhar para esses valores?”

⭐ Comece por estas

AggregationSignificado simplesQuando usar
MinMenor valor observado.Para identificar o menor resultado registrado.
MaxMaior valor observado.Para encontrar picos ou o maior valor.
AvgMédia dos valores.Para obter uma visão geral do comportamento.
MedianValor central dos dados ordenados.Para observar um valor mais representativo do centro dos resultados.
RateTaxa em que determinado evento ocorre.Quando a métrica faz sentido como taxa ao longo do tempo.
95th percentileValor abaixo do qual ficam aproximadamente 95% das observações.Muito útil para observar tempos sem depender apenas da média.
🔎 Conheça outras Aggregations que podem aparecer

Std. Dev. — desvio-padrão; ajuda a observar o quanto os valores variam.

Increase — mostra o aumento de uma métrica dentro do intervalo analisado.

Cum. Count — contagem acumulada até determinado ponto.

Cum. Min — menor valor acumulado observado até aquele ponto.

Cum. Max — maior valor acumulado observado até aquele ponto.

Cum. Avg — média acumulada até aquele ponto.

Cum. Std. Dev. — desvio-padrão acumulado.

Outras opções podem aparecer conforme a métrica escolhida e a versão da ferramenta.

⚠️ Nem toda Aggregation faz sentido para toda Metric. Observe as opções oferecidas pelo Grafana para a métrica escolhida e pense no que você deseja descobrir.

27Uma analogia simples: notas de uma turma

Imagine que nossa Metric seja a nota de uma prova. Temos várias notas e queremos analisá-las de maneiras diferentes.

Min

Qual foi a menor nota?

Max

Qual foi a maior nota?

Avg

Qual foi a média da turma?

Median

Qual valor fica no centro quando organizamos as notas?
Os dados são os mesmos. O que mudou foi a maneira de resumir e observar esses dados. No Analysis do k6 acontece a mesma ideia.

28Entenda os percentis sem complicação

Além de Min, Max, Avg e Median, você pode encontrar opções como 75th, 90th, 95th e 99th percentile.

Imagine os valores organizados do menor para o maior. Um percentil ajuda a indicar até qual valor ficou determinada porcentagem das observações.

PercentilLeitura simplificada
75th percentile (p75)Aproximadamente 75% das observações ficaram até esse valor.
90th percentile (p90)Aproximadamente 90% ficaram até esse valor.
95th percentile (p95)Aproximadamente 95% ficaram até esse valor.
99th percentile (p99)Aproximadamente 99% ficaram até esse valor.
💡 Exemplo: se o p95 de uma métrica de tempo de resposta fosse 500 ms, interpretaríamos que aproximadamente 95% das observações consideradas ficaram em até 500 ms.

Percentis são úteis porque uma média sozinha pode esconder uma pequena quantidade de respostas muito mais lentas.

29Prática guiada: compare Avg × Max × p95

Vamos observar a mesma Metric de três maneiras diferentes.

1. Em Metrics, escolha uma métrica de tempo disponível no seu teste.

2. Em Aggregation, selecione Avg e observe o gráfico.

3. Sem trocar a Metric, altere a Aggregation para Max.

4. Depois selecione 95th percentile, se essa opção estiver disponível.

5. Compare os três gráficos/resultados.

🧠 Pergunta: por que Avg, Max e p95 podem mostrar valores diferentes se estamos analisando a mesma métrica?

A resposta é simples: os dados não mudaram; mudou a forma de resumir esses dados.

30Como ler qualquer gráfico sem complicação

Use este roteiro sempre que abrir um gráfico no Analysis:

1️⃣ Metric

O que está sendo medido?

2️⃣ Aggregation

Como esses valores estão sendo resumidos?

3️⃣ Unidade

Está em ms, req/s, VUs, porcentagem ou outra unidade?

4️⃣ Tempo

Como o valor se comportou durante a execução?

5️⃣ Mudanças

Existem picos, quedas, aumentos ou falhas?

6️⃣ Comparação

O que mudou quando a carga foi alterada?
Não tente decorar gráficos. Pergunte: “O que estou medindo, como estou olhando para os dados e o que eles estão me mostrando?”

⚠️ Se uma métrica não possuir dados nesta execução, não invente valores. Registre que a informação não estava disponível.

31Três perguntas para orientar sua análise

1. O sistema respondeu?

Use Checks e informações de falha para verificar se as condições esperadas continuaram sendo atendidas.

2. Como respondeu?

Observe métricas de tempo e outras informações de desempenho disponíveis.

3. O que mudou com mais carga?

Compare as execuções e procure alterações em tempos, taxas, falhas e comportamento.

32Funcionamento não é a mesma coisa que desempenho

✅ Funcionamento

O sistema respondeu conforme a condição que verificamos?

Exemplo: o Check esperava HTTP 200 e recebeu HTTP 200.

⚡ Desempenho

Como o sistema se comportou enquanto atendia à carga?

Exemplo: tempos, taxas e mudanças de comportamento conforme os VUs aumentaram.

⚠️ Um sistema pode responder corretamente e, mesmo assim, apresentar lentidão. Por isso analisamos Checks e métricas de desempenho em conjunto.

33Curiosidade: veja o Script

Abra rapidamente SCRIPT → View executed script.

As configurações feitas visualmente no Test Builder são transformadas em um script executável pelo k6.

Procure valores que você configurou, como:

executor: 'constant-vus'
vus: 5
duration: '10s'
💡 Você não precisa entender todo o código agora. O objetivo é perceber que existe programação por trás da configuração visual.

34E as outras abas?

Você pode encontrar outras áreas na tela de resultados. Neste primeiro teste, não precisamos aprofundar todas elas.

HTTP

Pode apresentar informações ou recursos relacionados às requisições HTTP. Dependendo da execução, pode não haver dados específicos nessa área.

Logs

Útil principalmente quando scripts registram mensagens para ajudar na investigação e depuração.

Browser

Relacionada a testes que utilizam recursos de navegador. Não é o foco deste primeiro teste.

Profile

Área mais avançada para investigação de profiling. Não aprofundaremos agora.

Recommendations

Pode apresentar recomendações de recursos ou melhorias quando houver algo aplicável ao teste.
🎯 Para esta atividade, concentre-se principalmente em Cloud Insights, Checks e Analysis.

35Registre sua evidência 📸

Registre evidências suficientes para mostrar o que foi executado e como você chegou à sua conclusão.

📸 Configuração/carga utilizada
📸 Resultado dos Checks
📸 Cloud Insights relevante
📸 Metrics + Aggregation + gráfico analisado
Uma boa evidência permite que outra pessoa entenda de onde saiu a sua conclusão.

36Aumente a carga e compare

Depois do primeiro teste, repita o procedimento alterando somente a quantidade de VUs. Mantenha a mesma URL, duração e demais configurações para facilitar a comparação.

CenárioVUsDuraçãoChecks/FalhasMétrica observadaO que mudou?
🟢 Leve510s
🟡 Média1010s
🔴 Maior2010s

Para comparar corretamente, procure usar a mesma Metric e a mesma Aggregation nas três execuções.

🧠 Se você comparar Avg em um teste com Max em outro, estará comparando formas diferentes de resumir os dados.

37Faça sua conclusão de QA 🧠

Depois de comparar as execuções, responda com suas próprias palavras:

1. O sistema continuou respondendo corretamente quando a carga aumentou?

2. Apareceram falhas? Em qual cenário?

3. Qual Metric e qual Aggregation você utilizou na comparação?

4. O que aconteceu com o comportamento dessa métrica quando os VUs aumentaram?

5. Qual foi a principal diferença entre os cenários?

6. Com base nas evidências, qual é a sua conclusão sobre o comportamento observado?

⚠️ Evite conclusões como “o sistema é perfeito” ou “aguenta qualquer quantidade de usuários”. Seu teste representa somente as condições que você realmente executou.

Uma boa conclusão de QA diz o que foi testado → como foi analisado → o que foi observado → quais evidências sustentam a conclusão.
